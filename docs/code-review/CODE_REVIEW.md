# CELANO PPT 代码审查标准与流程 v1.0

> 生效日期：2026-10-05 ｜ 适用范围：`src/`（React 19 前端）与 `server/`（Express 后端）
> 维护人：技术负责人 ｜ 修订方式：每月复盘后升版，改动同步到 `CHECKLIST.md`

---

## 0. 这套规范要解决什么

代码审查的目的**不是挑错，而是三件事**：

1. **拦住不可逆的损害**——资金算错、越权、数据丢失、线上崩溃。这类问题一旦上线，靠回滚救不回来。
2. **让第二个人知道这里的坑在哪**——CELANO 有大量非直觉设计（计费预扣、并发闸门、legacy 兼容层、黑白设计系统），审查是知识传递的唯一低成本途径。
3. **让代码库不继续变坏**——存量问题可以慢慢还，但新增代码必须比存量好。

因此本规范的执行原则是：**对"新增/修改的行"严格，对"存量代码"宽容但记账**。

审查标准必须贴合真实代码库，以下是本次实测结果，后续所有指标以此为起点。

| 维度 | 现状 | 评价 |

## 2. 角色与职责

| 角色 | 谁 | 职责 |
|---|---|---|
| **作者** | 提交 PR 的人（含 AI 辅助产出） | 自查通过、填写 PR 模板、提供自测证据、逐条回应审查意见 |
| **审查者** | 任意一名其他开发者 | 按 §6 逐域检查，标注级别，24h（工作日）内给出首轮意见 |
| **Owner** | 技术负责人 | 复核高危域（资金 / 鉴权 / 安全 / 设计令牌）；裁量例外通道；每月复盘 |

**硬性规则**：
- **任何人不得合并自己的 PR**（含 Owner）。
- 涉及 `server/billing.ts`、`server/auth.ts`、`server/userSession.ts`、`server/adminRoutes.ts`、`server.ts` 路由段的改动，**必须有 Owner 复核**。
- 涉及 `src/index.css`、`src/styles/*.css`、设计令牌的改动，**必须对照 `design/celano-ui-spec.html` 复核**。

## 3. 提交前门禁（作者 5 分钟自检）

在发起 PR 之前，作者必须本地通过：

```bash
npm run lint            # tsc --noEmit（Wave1 后含 ESLint）
npm run test:image      # 全量单测
npm run build           # 改动涉及前端构建/路由时必跑
```

并回答三个问题（写进 PR 描述）：

1. **我改动的接口/页面，手工验证过哪些场景？**（正常 / 边界 / 失败）
2. **这次改动可能波及哪些没被我碰到的地方？**（列出依赖方）
3. **线上出问题怎么回滚？**（配置开关 / 直接回退 / 需要清数据）

> 第三条答不上来的 PR，视为设计不成熟，退回。

## 4. PR 规范

### 4.1 粒度

| 改动量 | 要求 |
|---|---|
| ≤ 400 行 | 正常审查 |
| 400–800 行 | 作者需在描述中说明为何无法拆分，审查者有权要求拆 |
| > 800 行 | **默认退回**，必须拆成多个可独立合并、独立回滚的 PR |

例外：格式化、批量令牌替换（如色彩收敛）等**机械性改动**不受此限，但必须单独成 PR，不与逻辑改动混在一起。

### 4.2 描述模板

见 `.github/PULL_REQUEST_TEMPLATE.md`，强制包含：背景 / 改动 / 影响面 / 自测证据 / 回滚方案 / 风险等级自评。

### 4.3 提交信息

```
<type>(<scope>): <一句话说明>

type: feat | fix | refactor | perf | chore | docs | test | style
scope: billing | auth | ppt | canvas | workspace | admin | home | design | server | deps
```

示例：`fix(billing): 上游超时未退回预扣点数`

## 5. 审查意见分级与前缀

所有意见**必须以方括号前缀开头**，作者据此判断哪些必须修：

| 前缀 | 含义 | 处理规则 |
|---|---|---|
| `[BLOCK]` | 会导致资金损失、安全漏洞、数据丢失、线上崩溃、破坏已达标的基线 | **必须修，禁止合并** |
| `[MAJOR]` | 逻辑错误、明显性能退化、破坏设计规范、缺必要测试 | 应修；若转 follow-up 需 Owner 批准并记录 issue |
| `[MINOR]` | 可读性、命名、重复代码、缺注释、类型不严谨 | 应修，作者可协商 |
| `[NIT]` | 风格偏好、可选优化 | 作者可自行决定，审查者不得因此阻塞 |
| `[Q]` | 提问，可能不是问题 | 作者必须回答，无需修改代码 |
| `[PRAISE]` | 值得保留的好设计 | 不要求动作，用于沉淀模式 |

**合并条件**：`[BLOCK]` 全部清零 + `[MAJOR]` 全部清零或有 Owner 批准的 follow-up + CI 全绿 + 至少 1 名审查者 Approve。

**审查者礼仪**：
- 对事不对人，写"这段代码在余额为 0 时会算出负数"，不写"你怎么连这个都没想到"。
- 每一条 `[BLOCK]`/`[MAJOR]` 必须给出**具体位置 + 触发场景 + 建议改法**；只说"这里有问题"的意见无效。
- 区分"必须改"和"我会这么写"，后者标 `[NIT]`。

## 6. 领域审查标准

按**本项目真实风险**排序。每域列出必查项、本项目具体条款、常见反例。

### S — 安全与权限

**必查**
1. 每个新增 `/api/*` 路由必须：① 先 `requireUser` 鉴权；② 校验资源归属（`resource.userId === session.userId` 或管理员白名单）。**只查 session 不查归属 = 越权**。
2. 返回给前端的用户对象必须走 `publicUser()`，禁止泄露 `apiConfigs`、`apiKey`、密码哈希、凭证指纹。
3. 文件路径拼接必须 `path.basename()` + 前缀校验（正面样例：`server.ts:506-508`）。
4. 不得放宽 helmet CSP、限流阈值、请求体上限；确需放宽时，PR 必须写明理由 + 替代缓解措施。
5. 新增资金入口（充值、兑换、提现类）必须单独加严限流（现状：`/api/wallet/redeem` 5 次 / 5 分钟）。

**常见反例**
- 新增接口直接 `db.getX(req.params.id)` 后返回，不比对 owner。
- 为"前端方便"在返回体里加 `apiKey`。
- 把 `trust proxy` 无条件设为 `true`（会导致 `X-Forwarded-For` 伪造绕过限流）。

### M — 资金与计费（最高危）

**必查**
1. **顺序**：`chargeCredits` 成功 → 才发起上游调用 → 失败必须 `refundCredits` + 写审计流水（正面样例：`server.ts:554-582`）。
2. **整数化**：所有点数必须 `Math.floor(Number(x) || 0)`，禁止浮点运算、禁止直接 `+`。
3. **可审计**：每次余额变动必须有且仅有一条 `addUsage` 流水，`detail` 要能让人看懂发生了什么。
4. **必带测试**：涉及计费的 PR 必须覆盖四个场景——余额不足、上游超时退款、重复提交、金额为 0/负数。
5. **单源**：点数单价只能来自 `src/shared/imageSpecs.ts` 的 `IMAGE_COST`，禁止在路由里写魔法数字。

**常见反例**
- 先调上游、成功后再扣费（并发下可被薅穿）。
- `catch` 里只返回错误、忘记退款（用户钱没了还拿不到图）。
- 同一函数内多次 `getUserById` 再 `updateUser`（读-改-写非原子，并发下丢更新；待修样例：`billing.ts:43-46`）。

### C — 并发与异步

**必查**
1. 所有上游网络调用必须有超时：`fetch(url, { signal: AbortSignal.timeout(N) })`，禁止裸 `fetch`。
2. 生图类调用必须走并发闸门 `withImageSlot()`，不得绕过。
3. 后台异步任务（含 `void (async () => ...)()`）必须在最外层 `try/catch`，失败要退款 + 落状态，不得静默吞掉。
4. 定时器、`setInterval`、事件监听必须在 `req.on('close')` / `useEffect` cleanup 中释放（正面样例：`server.ts:472-473`）。
5. 进程级 `Map`/缓存必须有上限或淘汰策略，禁止只增不减（待修样例：`server.ts:206` `activePersist`）。
6. ID 生成必须防碰撞：用 `crypto.randomUUID()` 或 `crypto.randomBytes`，禁止 `'user_' + Date.now()`（同毫秒注册会撞号；待修样例：`server.ts:242`）。

### T — 类型与 TypeScript

**必查**
1. **新增代码零 `any`**：不得新增 `: any` / `as any`。存量 113 处只减不增，并在 Wave2 分批清零。
2. **禁止 `!.` 非空断言**，除非上一行就是显式判空或类型守卫。
3. 来自 `req.body`、`JSON.parse`、上游响应的值，必须 `as unknown as T` 后**先收窄再使用**，禁止直接断言。收窄逻辑优先放进 `src/shared/` 的解析函数并配单测。
4. 领域类型集中在 `src/types.ts`，禁止在组件里重复内联定义同名结构。
5. 联合类型优先于布尔开关堆叠（`status: 'planning' | 'generating' | 'done' | 'failed'` 优于 4 个 boolean）。

**路线**：`tsconfig` 逐步开启严格性 → 先 `noUnusedLocals` + `noImplicitOverride`，再 `strict`，最后 `noUncheckedIndexedAccess`。**不得一次性全开**导致数百错误无法收敛。

### F — 前端（React 19）

**必查**
1. `useEffect` 依赖数组完整；有订阅 / 定时器 / 事件监听 / AbortController 必须 cleanup。
2. 列表 `key` 用稳定 id；**禁止用 index 作为可排序/可删除列表的 key**。
3. 弹窗必须具备：`role="dialog"` + `aria-modal` + Esc 关闭 + 焦点陷阱 + 关闭后焦点归还触发元素（可复用 `src/hooks/useFocusTrap.ts`）。
4. 交互元素必须是 `<button>`，**禁止 `div onClick`**（当前 0 处，禁止回退）。
5. `<img>` 必须带 `width`/`height` 或 `aspect-ratio`（防 CLS）；大图走 `loading="lazy"`。
6. 新增路由页面必须 `lazy()` 懒加载（现状 11 个路由已全部懒加载，禁止改回静态 import）。
7. 破坏性操作（删除作品、清空数据）必须二次确认，且失败要可重试。
8. 表单 label 必须 `htmlFor` 关联（当前 25 个 label 仅 1 个关联，新增表单禁止再欠债）。

### P — 性能

**必查**
1. 新增 npm 依赖需说明体积成本；**单个依赖 > 100KB(gzip) 需 Owner 批准**。
2. 大 base64 图片、大数组不得进入高频渲染路径的 state；优先引用 URL / 句柄。
3. 画布、长列表的重渲染用 `memo` / `useMemo` 兜住，避免在 render 里做重计算。
4. 服务端同步阻塞操作（大文件 `readFileSync`、大 Buffer 拼接）不得出现在请求主线程的高频路径。

### D — 设计系统一致性（CELANO 特有）

1. **颜色只走 `src/index.css` 的令牌**，禁止硬编码 hex（全站色彩已收敛，禁止回退）。
2. **主行动按钮永远黑白反转，绝不着色**——这是硬约束。
3. **每屏只允许一个 E4 反转元素**（主行动）。
4. 状态表达用**边框形态**（生成中=2px 澜青呼吸 / 已完成=1px 细线 / 失败=1px 虚线+红字），不用语义色填充。
5. 间距、圆角、动效曲线走既有阶值（8pt 网格 / 圆角 6·10·12·16·22·999 / standard·enter·exit·overshoot 曲线）。
6. 点缀色（澜青）、危险色（朱砂）、数据色（涨红跌绿）**三套色不得出现在同一视觉单元**。

### Q — 测试

1. 新增**纯逻辑**（计费、尺寸校验、解析、并发调度、ID 生成）必须带 `node --test` 单测，放在同目录 `*.test.ts`。
2. **修 bug 必须带一个回归测试**——先写一个能复现该 bug 的失败用例。
3. 测试不得依赖真实上游 API 与真实网络；必须 stub/mock。
4. 测试断言行为，不断言实现细节（不测私有变量、不测调用次数除非必要）。

### O — 可观测性与文档

1. 用户可见错误文案：中文、可读、可执行（"点数不足：本次需要 5 点，当前余额 2 点"），**禁止抛堆栈、内部 ID、上游原始报文**。
2. 服务端日志禁止打印 `apiKey`、密码、完整 data URL、身份证/手机号明文。
3. 注释写"为什么"，不写"做什么"（`server.ts` 顶部安全加固注释是正面样例）。
4. 非直觉决策、历史包袱、兼容层必须写注释说明**存在原因与删除条件**。
5. 魔法常数集中到 `src/shared/`，禁止散落（待修样例：`server.ts:152` 默认 200MB 与实际 64MB body 上限不一致）。

## 7. AI 生成代码的特别规则（本项目重点）

CELANO 相当比例的代码由 AI 辅助产出，这类代码有固定的失效模式，必须专项审查：

1. **不得整块接受**：AI 产出必须逐行读，尤其是路由、计费、鉴权三类代码。
2. **要求"影响面清单"**：让 AI 列出它改动的所有文件与原因，人工核对是否误改了无关文件。
3. **兼容层必须带"死亡日期"**：AI 倾向于不断加兼容层（如 `legacyPresentationView`），审查时要求标注删除条件与时间，禁止无限堆积。
4. **重点扫三类 AI 典型缺陷**：
   - 过度兜底——`catch {}` 吞异常、失败静默返回默认值；
   - 重复实现——再造一个已存在的工具函数（审查时先查 `src/shared/` 与 `server/` 是否已有）；
   - 为过类型检查而 `as any`——这是把问题藏起来，不是解决问题。
5. **大改必须拆分**：AI 一次产出 800+ 行时，拆成多个可独立回滚的 PR。
6. **UI 改动对照设计规范**：AI 生成的界面必须对照 `design/celano-ui-spec.html` 复核令牌与强调阶梯。

## 8. 审查流程

```
① 建分支  feat/fix/chore/refactor/docs + scope
      ↓
② 本地自检  lint + test + build（见 §3）
      ↓
③ 发起 PR  填模板，≤400 行，附自测证据
      ↓
④ CI 门禁  tsc + eslint + test + build（Wave1 起强制）
      ↓
⑤ 审查     1 名审查者；高危域 + Owner 复核（见 §2）
      ↓
⑥ 作者回应 逐条回复：已修 / 不修（附理由）/ 转 issue（附编号）
      ↓
⑦ 复核     审查者确认 [BLOCK]/[MAJOR] 已闭环
      ↓
⑧ 合并     Squash merge，删除源分支
```

**时效（SLA）**

| 环节 | 目标 |
|---|---|
| 首轮审查响应 | 工作日 24 小时内（P0 热修：1 小时内） |
| 作者回应意见 | 24 小时内 |
| PR 存活时长 | 中位数 ≤ 2 天 |

**例外通道（热修）**
线上 P0 故障可"先合并、后补审查"，但必须满足：① 改动 ≤ 50 行且仅限故障点；② 合并后 **24 小时内补齐 PR 描述与审查**；③ Owner 记录进月度复盘。热修通道每月使用 > 2 次，说明发布质量出了问题，需回头查 §3 门禁。

**抽查复审**
Owner 每月随机抽 5 个已合并 PR 做二次审查，重点看 `[MINOR]`/`[NIT]` 是否被长期忽略——这类意见积压是代码库腐化的前兆。

| 指标 | 起点（2026-10） | 3 个月目标 |

## 10. 落地路线

| 阶段 | 内容 | 产出 |
|---|---|---|
